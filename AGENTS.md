# Instructions for coding agents

This file applies to any automated contributor. Read it before changing the repository. People contributing by hand
will also find it a short list of what the checks expect; [CONTRIBUTING](docs/CONTRIBUTING.md) has the rest.

## Working rules

- Work on a branch named `feature/<slug>`, `bugfix/<slug>`, `docs/<slug>`, `chore/<slug>`, `agent/<slug>` or (to find
  something out, never to merge) `spike/<slug>`, with a lower-case slug and hyphens. The `branch-names` ruleset enforces
  the prefix. Never commit to `develop` or `main` directly.
- Commit with `git commit -s`. Write the subject in the imperative, 72 characters or fewer, and the body as a plain
  description of what changed and why. The only trailer is `Signed-off-by`; add no other line, no "generated by"
  footer and no co-author. The `Policy` check fails them.
- Before pushing, commit and run `python3 tools/ci/precheck.py`. It runs the static checks of the pull request gate on
  your commits (it finds `icl-common-infra` beside this checkout, or in `ICL_COMMON_INFRA`).
- Open pull requests against `develop`. Fill in the pull request template, and end the body with a sentence, not a
  `Word: value` line (the text policy reads that as a trailer). Squash merge through the merge queue is the only
  method: `gh pr merge <n>` queues a pull request whose checks are green. The required checks are `CI Status` and
  `Scan dependency diff` ([branch protection](docs/branch-protection.md)).
- Build and test with the presets in `CMakePresets.json` (`linux-gcc-debug`, `windows-msvc-debug`,
  `macos-clang-debug`; `windows-msvc-fastdebug` and its Linux and macOS siblings are quicker to iterate with). A change
  to code runs the preset for the machine at hand, and `ctest --preset <name>`, before the pull request
  ([getting started](docs/getting-started.md)). Run the Qt test binaries through `ctest`, not by hand.
- Do not create or edit secrets, tags, releases, repository settings or rulesets. The owner does those.
- Do not change what the program does without the owner's say: the solver's results, the screens and their wording, the
  saved settings or the diagnostics file format. Tests that pin them are not edited to make a change pass.
- Do not edit `cmake/icl/`. It is copied from `icl-common-infra`; change that repository, then run
  `python3 tools/ci/sync_cmake.py`. The shared workflows `ci.yml` calls are pinned to a commit of that repository;
  `python3 tools/ci/repin.py` moves the pin.

## Code rules

- C++23, extensions off. The standard for all projects is
  [`docs/standard.md`](https://github.com/iainchesworthlabs/icl-common-infra/blob/develop/docs/standard.md) in
  `icl-common-infra`. This repository keeps the conventions it already had, which the standard allows:
  - Format: the repository's `.clang-format`. Run `clang-format` (23.1.3 is the CI version) on the `.cpp` and `.hpp`
    files you changed. `.clang-tidy` is checked by CI over everything but the Qt app.
  - Names: [CONTRIBUTING](docs/CONTRIBUTING.md#code-style) lists them, and `.clang-tidy` checks them. The code that QML
    sees under `src/app` is `camelCase`.
  - Return `Result<T>` (`std::expected`) for failures that are expected; do not throw for them.
- Add no new `#if`, `#ifdef` or `#elif` on a platform, a compiler or a library version. CMake chooses the platform
  code (`src/app/platform/<os>/`, [platform isolation](docs/platform-isolation.md)). On Windows run
  `tools/checks/check_platform_isolation.ps1`; CI runs the same check.
- Qt belongs in `src/app`. `src/lib` (`cube::lib`) has no GUI and no platform code.
- A string the user sees goes through `qsTrId` with a literal id (never a variable), and the words are written once, in
  `docs/design/strings.json` ([translations](docs/i18n.md)).
- A control on screen needs a system test that presses it: the `system.reach` check fails on a control nothing taps.
- New behaviour comes with a test ([testing](docs/testing.md)). CI holds line and branch coverage at 80%.

## If you change X, update Y

| You change | Also update |
|---|---|
| A behaviour a person using the app would notice | A fragment in `changelog.d/` (`<slug>.<type>.md`; see its `README.md`), or label the pull request `no-changelog` before the first push |
| A public header in `src/lib/include` | The tests, and `docs/architecture.md` when the layout changes |
| A CMake option or preset | `docs/getting-started.md` and `docs/building.md` |
| A toolchain version | `.github/toolchain-versions.json`, then `docs/ci.md`; `tools/ci/check_toolchain_versions.py` checks the workflows against it |
| A workflow in `.github/workflows` | `docs/ci.md`; pin every `uses:` to a full SHA with a version comment; a job that `CI Status` should wait for goes in its `needs` and `expected` |
| `release.yml`, a signing variable or a secret name | `docs/releasing.md` |
| A dependency in `vcpkg.json` | `docs/licensing.md` when the set of shipped components changes; the baseline check and Dependabot cover the fork |
| Test labels, or coverage | `docs/testing.md` |
| A platform file, or a `src/app/platform/` directory | `docs/platform-isolation.md` |
| The Linux, Windows or macOS package files or their dependencies | `docs/packaging.md` |
| A string the user sees | `docs/design/strings.json`, then `python tools/i18n/strings_to_ts.py --write` for the ten catalogues, then `python docs/design/tools/build.py` to refresh `content.md` and the prototype |
| A language | `docs/i18n.md` and `docs/i18n-lanes.md` |
| The wording or layout of a screen | `docs/design/screens/<screen>.md`, and the guide page under `docs/guide/` when a person would follow it |
| Who may report a vulnerability, or the signing key | `SECURITY.md` and `docs/SECURITY.md` |
